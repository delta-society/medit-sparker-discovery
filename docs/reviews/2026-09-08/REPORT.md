## F1 · P1 — CRLF 문자열을 저장하면 해당 과제를 다시 읽을 수 없음

위치: `plugin/scripts/plan.py:348`, `:442`, `:509`, `:591`. 같은 줄바꿈 처리 방식이 legacy 렌더러와 `plugin/scripts/linkage.py`에도 있다.

재현:

1. 정상 linked 과제를 r1으로 저장한다.
2. `user_result.result`를 `First line\r\nSecond line`으로 바꾸고 정상적인 expected revision과 이유를 제공해 update한다.
3. r2 JSON/Markdown은 디스크에 공개되지만 CLI는 `Markdown/JSON 불일치`로 exit 2를 반환한다.
4. 이후 show도 동일하게 실패한다. load를 공유하는 resume/history/export와 후속 수정도 해당 기록을 정상 소비하지 못한다.

원인: 렌더러는 LF만 ` / `로 바꾸므로 CR이 남는다. 저장된 Markdown을 `Path.read_text()`로 읽으면 universal newline 처리가 CR을 LF로 바꾼다. 그 결과 자체 생성한 문서가 재렌더링 문자열과 다르다고 판정된다. 완성 리비전 rename 뒤에 readback하므로 오류를 보고해도 이미 잘못된 r2가 남아 있다.

영향: Windows 계열 줄바꿈이 보존된 복사·붙여넣기/파일 기반 입력만으로 발생할 수 있다. 이전 리비전 바이트는 남지만 정상 CLI의 과제 접근은 막힌다. 운영체제가 Windows일 필요는 없으며 Debian에서도 재현했다. 실제 호스트 모델이 항상 CRLF를 전달한다는 뜻은 아니다.

수정 방향: 검증 시 파일 바이트 또는 newline 변환 없는 읽기를 사용해 저장 표현과 일치시킨다. 신규 렌더링에는 CR/LF를 일관되게 처리하고, **기존 리비전 렌더링 계약을 무심코 바꾸지 않는다**. staging 단계에서 실제 파일을 읽어 검증한 뒤 리비전을 공개하는 구조로 변경한다. 이미 기록된 문제 리비전은 원본을 보존하는 별도 복구 절차가 필요하다.

수용 시험: LF/CRLF/단독 CR이 각 출력 문자열에 포함된 new/update/finalize/export를 실행하고, 실패할 입력은 공개 전에 거절되는지 확인한다. 구버전 golden fixture와 기존 리비전 바이트 보존도 확인한다.

## F2 · P1 — ZIP 생성이 무시된 로컬 기록·환경 파일까지 포함

위치: `scripts/build-package.py:12–18`.

재현: 임시 소스 복사본의 `plugin/.env`와 `plugin/.sparker-discovery/case-synthetic/r000001/plan.json`에 가짜 표식을 만들고 build한다. ZIP 검사까지 성공하고 두 파일 모두 ZIP 엔트리에 포함된다. 실제 환경 파일·실습 기록은 읽지 않았다.

원인: `plugin.rglob('*')` 결과에서 Python 캐시만 제외한다. Git 추적 여부, `.gitignore`, 배포 허용 파일 목록은 적용하지 않는다. 플러그인 디렉터리에서 실습하거나 개발용 설정을 두고 패키징하면 이 조건이 만들어질 수 있다. 플러그인 밖의 일반적인 저장 경로까지 자동 포함하는 것은 아니다.

영향: 배포 과정에서 ZIP을 공유하면 로컬 비공개 파일이 함께 전달될 수 있다. 현재 저장소에 그런 자료가 존재하거나 이미 배포됐다는 증거는 없다.

수정 방향: 배포할 manifest/skills/references/scripts/승인 예시/가이드의 명시적 목록 또는 엄격한 경로별 허용 규칙을 사용한다. 민감 파일·실습 폴더·임의 ZIP의 혼입은 검사에서 실패시킨다. examples와 guide도 동일하게 링크·경로 정책을 적용한다. 단순 `.env` 제외만으로는 임의 이름의 실습 기록까지 해결되지 않는다.

수용 시험: 가짜 `.env`, `.sparker-discovery`, 임의 비공개 파일을 섞은 복사본을 패키징해 혼입 거절/배제를 확인하고, 정상 ZIP의 엔트리 목록 및 해제 후 helper 실행을 검증한다.

## F3 · P2 — 2MB 입력 제한과 저장 레코드 크기가 달라 과제 접근이 막힘

위치: `plugin/scripts/plan.py:75–78`, `:497–510`, `:591`.

재현: 정상 r1에 대해 구조가 유효한 **1,999,950바이트** 입력 JSON을 update한다. 입력 제한을 통과하지만 레코드 메타데이터와 들여쓰기가 추가된 r2 JSON은 **2,001,605바이트**가 된다. update는 `JSON은 2MB 이하만 허용`으로 실패하고, 이후 show도 실패한다. r1은 남아 있다.

원인: 입력 plan과 저장 record 모두 read_json의 2,000,000바이트 제한을 쓰는데 write는 직렬화된 record 크기를 공개 전에 검사하지 않는다. 파이썬 API 직접 호출은 입력 파일의 크기 검사조차 거치지 않는다.

영향: 긴 제출문/누적 기획을 처리할 때 또는 큰 입력을 의도적으로 제공할 때 발생한다. 정상 CLI 재개·수정이 막히며 오류 이후에도 상태가 변한다. F1과 공개 후 검증이라는 원인을 공유하지만 바이트 크기 계약은 별도로 수정해야 한다.

수정 방향: 실제 저장할 UTF-8 record의 크기를 staging 단계에서 확인해 read/write 계약을 맞춘다. 입력 한도와 내부 레코드 한도를 분리하는 방법도 가능하다. 실패 시 기존 최신 리비전이 계속 읽히고 수정 가능해야 한다.

수용 시험: 한도 직전/동일/초과 크기를 ASCII와 한국어로 각각 실행한다. new/update/finalize에서 메타데이터 증가도 포함하고, 실패 이후 revision·show·다음 정상 수정이 그대로 동작하는지 검증한다.

## 설계상 주의점 — 확정 결함과 구분

1. **연결되지 않은 확보 작업은 인계 Markdown에서 사라진다.** 새 acquisition task를 JSON에 넣으면 complete/finalize가 통과하지만 inputs 또는 objective/linkage의 구조적 참조가 없으면 export에 나오지 않는다. `test_optional_private_data_not_rendered_or_required_complete`에서 의도적으로 보호하는 비공개 레거시 정보 필터이므로 이를 일괄 출력하도록 바꾸면 안 된다. 신규 기획의 업무 규칙·환경 확인 작업까지 누락시키지 않으려면 작업별 공개/비공개 범위나 참조 계약을 명확히 해야 한다. 현재 재현은 누락 동작의 증거이며 실제 참가자에게 필수 작업이 전달되지 않았다는 증거는 아니다.
2. **빈 linked template에는 submission/facts가 없고, 첫 저장 후 submission을 새로 추가할 수 없다.** 코드가 최초 원문 불변을 비교하므로 None에서 객체로 바뀌는 것도 거부한다. 문서에는 facts로 보충하는 경로가 있고 blank template 저장도 명시적으로 허용돼 있어 신규 취약점으로 분류하지 않았다. 정상 첫 대화에서 원문이 저장됐는지, 원문이 늦게 제공되면 facts에 출처와 함께 남는지는 실제 호스트 QA가 필요하다.

## 미검증과 해석 한계

- 실제 Claude Code 모델의 prompt injection 저항성, 전체 대화·설치·재개·사용자 확인 흐름은 실행하지 않았다. 정적 지침과 helper 동작만으로 프롬프트 주입 방어 성공을 주장하지 않는다.
- 호스트 파일/셸 도구가 제공하는 권한은 Python helper의 검사와 별개다. helper가 제출문을 실행하지 않는 사실은 호스트 모델의 모든 도구 사용을 제한한다는 뜻이 아니다.
- 확인 JSON의 actor/quote와 해시는 사람 신원을 인증하지 않는다. 이 한계는 계약에 명시돼 있으므로 합성 확인 파일이 통과하는 것을 새로운 인증 우회 취약점으로 세지 않았다.
- 문자열 구조 검사로 업무 판단·인과 가설·실제 발화의 진실성을 보증할 수 없다. 의미적으로 그럴듯한 허위 기획서를 검출하지 못할 수 있다는 점은 별도의 사용자 검토/호스트 QA 대상이다.
- 강제 종료 뒤 잔존 lock 수동 해제, 적대적 동시 파일 경로 교체 비지원은 문서에 명시돼 있다. 전원 장애 내구성, 실제 Windows/macOS, 실제 업무 앱 연결은 이번에 검증하지 않았다.
- 문서에 과거 0.3/0.4 요구사항이 함께 남아 있다. 현행은 KPI 확인과 기존 앱 재사용·결과/근거 기록이며 외부 전달처는 선택이다. 기술 상세 미확인은 후속으로 넘길 수 있다. 의미 수준에서 이 경계가 대화 중 일관되게 적용되는지는 별도 시험이 필요하다.

우선순위: F1 저장 안정성과 F2 패키징 경계를 먼저 수정하고, 같은 저장 트랜잭션 변경에서 F3도 해결한다. 이후 실제 호스트에서 악성 제출문·KPI 수정·확정 거절·재개를 포함한 다회 대화 시험을 수행한다.
