# 0.5.5 Linux 활용 흐름 검토

대상: `/tmp/discovery-live-qa/runs/linux-055-reuse/`, ZIP SHA-256 `49578b41bd10617837a76c0ca7edfd5355bf0b918cabe0b8ae7c269614883037`. Claude Code `2.1.263`, 모델 `claude-sonnet-4-6`, Linux x86_64 disposable-container의 실제 대화다. 같은 버전의 별도 native 실행을 이 결과로 대체하지 않는다.

## 선택 범위 보정 — reuse-unknown 3턴 PASS

T1은 원문 범위·역할·미확인 수치를 재사용하고 활용 후보를 가설로 제안했다. 현재 수동 방식이나 기존 승인/수정 절차를 원문 사실로 붙이지 않았다. T2 “아직 모름”은 미확정으로 유지하고 알려진 범위의 초안을 진행했다.

T3 사용자 선택 이후 r3 전체 계획을 대조했다. 이전 0.5.4의 선행 생산 기능 유지 문제는 이 실행에서 해소됐다.

| 필드 | 실제 r3 내용 |
|---|---|
| selected_change | 기존 ST Excel 공정 기록 읽기 → 유사 공정 조건·출처·근거 검색/표시 |
| non_goals | 새 편차 계산·누락/이상치 생성, 패턴/분포/추세 분석, 검토 자동 수집, ST 값 생성 명시 제외 |

## 후속 케이스 실행 상태

`reuse-confirmed-time` T1에서 CLI는 종료 코드 0과 저장 완료 응답을 반환했지만, 그룹 state에 턴 성공이 기록되지 않고 중단됐다. 이벤트의 최초 입력 JSON 시험 ID가 `T-normal-01`/`T-exception-01`이어서 helper가 ID 오류를 반환했다. 모델은 과제 ID를 `case-st01`에서 `case-stex`로 바꿔 재시도한 뒤, 실제 원인이었던 시험 ID 소문자 변환과 metric_reference 정합성을 고쳐 `case-stex/r000001` 저장에 성공했다. 기존 `.sparker-discovery/case-st01`은 리비전 없는 빈 디렉터리로 남았다.

이 상태는 scope 선택 3턴의 통과를 무효화하지 않지만, 전체 9턴 성공으로 집계할 수 없다. 이후 runner 보정과 별도 재실행으로 검증했으며 아래에 분리 기록한다. 공개된 리비전을 삭제하거나 증거를 정리해 성공처럼 바꾸지 않았다.

## 별도 재실행 — 같은 ZIP, linux-055-reuse-retry

`/tmp/discovery-live-qa/runs/linux-055-reuse-retry/`는 같은 ZIP SHA-256의 별도 실행이다. 앞 실행의 중단 증거를 지우거나 재해석하지 않는다.

`reuse-confirmed-time` 2턴의 구조와 의미를 검토했다. 분/건 감소 목표를 유지하고 실제 미확인인 “1건” 단위만 물었다. T2는 분모를 임의 확정하지 않고 공정수·라인수를 기록해 단위 확인 뒤 사용할 초안을 제시했다. 기록 위치·수동 입력/자동 타임스탬프는 획득 작업으로 남겼다. 중단 원인·재시작 여부도 보존하도록 제안했다. r1/r2 모두 draft, objective proposed/confirmation=null이다. 수작업 병목은 h02의 ai_hypothesis이고 인과 관계가 이를 명시 참조하므로 확인된 현재 사실 날조로 세지 않는다. 이 케이스의 목표 보존·미확정 유지 계약은 PASS다.

`reuse-one-off` 2턴 PASS: 일회성 Word 형식 정리, 코드/반복 자동화/축적/새 시스템/발송 제외를 유지했다. 형식 예시는 합성·기준 미확정으로 표시했고 실제 기준을 물었다. T2는 같은 r1을 읽고 유지했다. 정상 형식 적용·기준 미확보 예외 시험이 선택 범위에 맞으며, 원문에 없는 현행 승인 과정을 확정된 사실로 추가하지 않았다.

`reuse-weekly-report` 2턴 PASS: T1 원문과 가설을 구분했고 T2 사용자 선택 후 기록·기존 Excel 이력 조회로 좁혔다. ST 추정·대시보드·사전 알림은 제외됐고 코드/구현/정상·중복 예외 시험이 해당 기록·조회 기능에 연결된다. 현재 수동 취합을 원문 사실로 단정하지 않았다. KPI는 주간 누락 지표 발생 건수 감소라는 미확인 초안으로 제안하고 사용자 확인을 요청했다. 실제 검토 사용을 직접 측정하는 지표는 아니므로 향후 기록 누락과 실제 누락 감소를 구분하는 보완 여지는 있지만, 단순 기록량을 늘리는 목표나 확인된 사용자 목표 날조로 판정하지 않는다.

## 검토 결론

최종 ZIP의 핵심 4케이스 9턴은 **첫 실행의 reuse-unknown 3턴 + 별도 retry 6턴**에서 계약 범위 PASS다. retry 자체는 구조 PASS이다. 첫 실행의 추가 실패 턴을 성공 턴으로 세거나 한 번의 연속 9턴 실행이 통과한 것으로 쓰지 않는다. 현재 검토한 범위에서 새 P1/P2는 찾지 못했다. 이후 native07의 같은 ZIP 결과는 별도 검토한다.
