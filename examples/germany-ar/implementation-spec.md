# 독일법인 입금·매출채권 검증 — 개발 착수용 명세 초안

상태: 업무 방향은 사용자 확인. 아래 상세 설계는 AI 제안·합성 시험 완료이며 현업 규칙 확정·실거래 검증·운영 투입 승인이 아니다. 종전 사람 확정본(case-4162bb7c revision9)은 보존하고 이번 상세화는 다시 초안으로 검토한다.

## 1. 해결할 작업과 첫 구현 범위

사용자는 SAP 입금 반영 확인·수정과 딜러 회수 요청 담당자다(직책·분업 미확인). 오전·오후 각 1회, 회당 약1~2시간이라는 자기보고를 받았다. 준비·검토 포함 범위와 단계별 비중은 미확인이다. 확인된 시간 집중 구간은 자료 추출·정리와 입금-인보이스 짝 찾기다. 적요의 인보이스 번호를 먼저 보고, 합산 입금은 없고 분할 입금은 있으며 aging은 지급기일 기준이다.

첫 구현 제안은 담당자 PC의 파일 기반 검토 도구다. SAP·Citibank 파일 다운로드는 남고, 열 대응 저장·형식 정리·중복 검사·인보이스 대조·분할 입금 합산·두 검토 목록 생성은 코드가 수행한다. 자료 추출 자체의 시간을 줄였다고 주장하지 않는다. API 자동 수집은 현재 지원·권한 확인 작업으로만 두고 첫 구현의 필수 조건에서 제외한다.

자동 SAP 반제/전표 수정, 딜러 연락, 은행 거래, 환산·수수료·차감의 자동 판단, 여러 인보이스에 대한 합산 배분은 제외한다. 지원하지 않는 거래는 확인 대상으로 남기며 삭제·0 처리하지 않는다. 제품 실행에 LLM은 우선 사용하지 않는다. AI는 개발과 초기 열 대응 초안 작성에 사용하고, 실거래는 LLM에 전송하지 않는 설계를 제안한다.

## 2. 대표 업무 한 건 — 합성 입력에서 사람 행동까지

아래 이름·번호·금액·날짜는 모두 합성이다. 실제 고객 거래/성과가 아니다. 실제 실행 입력은 `executed/input.json`, 출력은 `executed/result.json`·`executed/result.md`다.

기준일 2026-09-07, 동일 마감 기준의 자료라는 가정. Dealer-A / DE01 / INV-101 / EUR / 지급기일 2026-09-01. SAP 미결 잔액은 600.00이다. 은행 T1은 400.00이며 SAP에 이미 반영됐고 T2는 300.00이며 아직 반영되지 않았다. SAP 반영 여부는 **합성 입력이 제공한 증거 상태**이며 실제 어댑터가 이를 자동 판정한 것이 아니다.

1. 담당자가 SAP와 은행 자료를 선택하고 기준시점을 확인한다. 시스템은 열 누락·동일 ID 내용 충돌·기준시점 차이를 검사한다.
2. 적요의 번호 후보를 회사코드·인보이스와 대조한다. 실제 적요 형식이 없으므로 이번 실행 예제는 추출된 번호를 입력받는다. 정규식이 모든 적요에서 동작했다고 주장하지 않는다.
3. SAP 장부 잔액 600.00은 보존한다. 이미 반영된 T1은 다시 차감하지 않는다. 미반영 T2 300.00을 별도 합산한다.
4. 담당자는 아래 출력에서 T2를 열어 원천 근거를 보고 SAP 반영 필요 여부를 확인한다. SAP 수정은 현행 권한으로 별도 수행한다.
5. 잔여 300.00은 지급기일 경과 6일의 회수 검토액이다. 담당자가 미배분·분쟁·후속 입금 등을 확인한 뒤 딜러에게 연락한다. 화면 금액만으로 회수 요청을 발송하지 않는다.

### 결과 화면/Excel 출력 예시 — 제안, 아래 수치는 실행 결과

|딜러|인보이스|통화|SAP 장부 미결|은행 미반영 입금|회수 검토 잔액|연체일수|상태|근거|
|---|---|---|---:|---:|---:|---:|---|---|
|Dealer-A|INV-101|EUR|600.00|300.00|300.00|6|SAP 반영 확인 / 회수 전 검토|T1·T2|
|Dealer-B|INV-102|EUR|500.00|0.00|500.00|0|기일 미경과|해당 은행 행 없음|

같은 작업면에 인보이스 상세와 딜러별 요약을 둔다. 은행 행이 없다는 것은 입금 없음의 증거가 아니다. 딜러별 요약은 통화별로 분리하고, SAP 연체 잔액과 회수 검토 잔액을 별도 열로 출력한다. 기일 누락·과입금·입력 예외가 있으면 요약도 불완전 표시한다. 임의 aging 구간을 만들지 않고 초기에는 연체일수와 기일 경과 합계만 제공한다. 현행 구간은 확인 후 적용한다.

### 사람이 처리하는 상태 — 구현할 UX 계약

`미검토 → 근거 확인 → SAP 수정 확인 또는 회수 검토 완료`로 진행한다. 오류 발견 시 `재검토`로 되돌린다. 복수 후보는 연결 후보와 원천 행을 보여주고 담당자가 선택해야 한다. 수동 연결/취소는 거래 ID·대상 인보이스·판단 이유·담당자·시각을 추가 기록하며 원본을 덮어쓰지 않는다. 다음 반입에서 원천 내용이 바뀌면 이전 완료 판단을 승계하지 않고 재검토로 되돌린다. 이 상태 저장·수동 연결 UI는 명세이며 이번 계산 검증 코드에는 구현하지 않았다.

## 3. 데이터 계약과 처리 규칙

실제 SAP/Citibank 열 이름은 아직 확인하지 않았다. 다음은 내부 표준 필드 제안이며 원천 열과의 매핑은 익명 샘플로 확인한다.

|대상|필수 표준 필드|의미·식별 규칙|
|---|---|---|
|SAP 인보이스 스냅샷|company, invoice, dealer, currency, sap_open, due, as_of|회사+인보이스를 임시 유일키로 사용. 실제 회계연도/전표항목 필요 여부 확인. sap_open은 해당 시점 미결 잔액. due 누락은 null/빈값이며 임의 대체 금지|
|은행 거래|company, account, txn_id, invoice, dealer, currency, amount, date, status|회사+계좌+거래ID. invoice는 적요에서 추출/사람 확인한 후보. booked 거래만 자동 대조|
|SAP 반영 근거|sap_reflected=yes/no/unknown, 근거 전표/조회시점|실제 데이터에서 근거 없으면 unknown. Payment Date만으로 yes/no를 판정하지 않음|
|원천 추적·사람 판단|원본 파일 식별값·행 위치·반입시각·규칙 버전·연결/취소 이력|실물 구현 시 보존. 합성 코드의 evidence는 txn_id만 출력|

R1. 잔액의 기준은 **SAP 미결 잔액**이다. 전체 청구액에서 모든 과거 입금을 재구성하는 방법과 혼합하지 않는다. 실제 현장에 이 잔액·반영근거가 없으면 해당 대조를 미확인으로 낮추고 필요한 SAP 조회를 확보한다. 실물 데이터 전에는 어댑터 설계를 확정하지 않는다.

R2. `회수 검토 잔액 = SAP 미결 잔액 − 동일 기준시점의 확실한 미반영 은행 입금 합계`. 이 값은 장부 잔액이 아니다. SAP에 반영된 거래는 이 식에서 제외한다. 음수가 되면 과입금 예외로 보내고 유효 잔액/자동 회수액을 출력하지 않는다.

R3. 동일 거래ID+동일 내용 재반입은 한 번만 반영한다. 동일 ID의 내용이 달라지면 처리 전체를 중단하고 새 정상 결과를 내지 않는다. 식별자가 없으면 날짜·금액이 같다는 이유만으로 중복 제거하지 않는다.

R4. 번호 미매칭, 다중 후보, 딜러/통화 불일치, 취소·정정, 반영상태 미확인, 기준일 이후 거래는 자동 배분하지 않는다. 하나라도 미배분 입금이 있으면 영향을 특정하지 못한 회수 목록은 잠정 표시한다. 환산·차감·수수료는 별도 규칙 확인 전 자동 처리하지 않는다.

R5. `연체일수 = max(0, 기준일−지급기일)`. 기일 당일은 0, 기일 누락은 미확인이다. 실제 시간대·은행 value date/booking date·SAP 추출시각 정합성은 확보 작업이다. 합성 코드는 일자 단위만 시험하며 오전/오후 시각 정합성은 검증하지 않았다.

금액은 부동소수점 대신 Decimal로 EUR 소수 둘째 자리까지 계산한다. 합성 예제의 통화 소수 자릿수 가정이며 모든 통화를 지원한다고 보지 않는다.

## 4. 입력과 예상 결과가 정해진 수용 시험

`python3 -m unittest discover -s examples/germany-ar -v`로 재실행한다. 실제 실행 결과 12개 시험 통과. 모든 데이터는 합성이고 정답은 본 문서의 제안 규칙에 대한 정답이다. 현업 규칙의 정당성은 별도 확인한다.

|시험|입력 변경|예상 결과|
|---|---|---|
|분할 입금|위 대표 사례|SAP600 / 미반영300 / 검토300 / 연체6 / 근거T1·T2|
|재반입|은행 T1·T2를 동일 내용으로 다시 추가|전체 결과가 첫 실행과 동일|
|거래 충돌|T1 금액만401로 바꾼 중복 행|conflicting content 오류, 정상 결과 생성 안 함|
|SAP 상태 미확인|T2 반영 상태unknown|미반영 합산0 / 잠정 표시 / SAP 확인 예외|
|미매칭·통화·딜러|T2 번호NO-SUCH 또는USD 또는Dealer-C|각각 예외1 / 자동 차감0|
|지급기일 경계|09-06 / 09-07 / 09-08 / 누락|연체1 / 0 / 0 / null|
|전액·과입금|T2=600 / 700|검토0 / 유효 검토잔액null·과입금 확인|
|스냅샷·중복 인보이스|SAP 기준일09-06 / 같은 키 추가|각각 오류로 중단|
|취소·미래일|T2 reversed / 09-08|각각 예외·차감0|
|잘못된 금액|NaN / Infinity / 음수 / 셋째 소수 / 문자|입력 오류|
|딜러별 aging|대표 사례|A 장부연체600·검토연체300 / B 둘 다0|
|실자료 오용 방지|synthetic=false|합성 시험 전용 오류|

후속 실제 어댑터 시험: 원천 적요 번호 추출·다중 번호, Excel 열 형식/수식, 계좌별 고유키, 실제 정정 거래, 중간 파일 실패·복구, 수동 판단 재개. 이 시험들은 아직 수행하지 않았다. 계산 예제를 제품 전체의 PASS로 확대하지 않는다.

## 5. 실행·보관·실패 처리 제안

첫 제품은 승인된 담당자 PC에서 단독 실행한다. 원본은 읽기 전용으로 두고 실행별 결과 폴더에 기준시점과 입력 식별값을 기록한다. 파일 선택·계산 실패 시 기존 성공 결과를 새 결과처럼 표시하지 않고 마지막 성공 시각과 실패 이유를 함께 보여준다. 현행 수작업이 복귀 경로다. 저장 위치·보존기간·접근권한은 사내 규칙 확인 후 정하며 외부 서버/LLM 전송을 기본으로 하지 않는다.

이번 실물은 Python 표준 라이브러리 계산 probe와 JSON/Markdown 출력이다. Excel·화면·로컬 판단 이력은 후속 구현 대상이다. `reconcile.py --output 새폴더`는 기존 결과를 덮어쓰지 않으며 검증 오류는 폴더 생성 전에 종료한다. 파일 쓰기 도중 OS 장애의 원자성·복구는 아직 검증하지 않았다. 실행에는 합성 입력만 사용한다.

## 6. 성공 기준과 구현 순서

제품 성공의 제안 기준: 같은 물량·같은 자료 기준시점의 처리에서 기존 검토와 잔액/매칭/aging이 일치하고, 준비·검토·재작업 포함 사람시간이 기존 방식보다 감소해야 한다. 시간 감소 목표치와 허용 처리시간은 담당자와 대표 물량을 확인해 결정한다. 목표치 미확정은 설계/합성 개발을 막지 않지만 성과 달성 주장을 막는다. 파일 다운로드 시간이 남는 점을 분리 측정한다.

1. 현재 완료: 대표 사례·표준 필드·기준 잔액 제안, 합성 정상/예외 시험과 계산 실행.
2. 다음: SAP·Citibank 익명 열 목록/샘플로 식별자·반영근거·조회시점·Payment Date 의미 확인. 담당은 실습 참가자가 실제 업무 담당과 확인(이름·기한 미확정).
3. 이후: 원천 파일 어댑터 → 출력·원천 근거 표시 → 수동 판단/재개 → 같은 자료로 병행 검증. 각 단계는 위 수용 시험과 실제 파일 회귀시험으로 확인한다.
4. 운영 전: 실제 데이터 권한·보관·실패 복구, 현행 정답표 대조, 대표 물량 처리시간 검증. SAP 수정/외부 연락 자동화는 포함하지 않는다.

## 7. 이번에 닫힌 것과 남은 결정

닫힌 것: 사례 하나로 입력→계산→출력→사람 행동을 연결했고 12개 합성 시험을 실행했다. 장부 잔액과 회수 검토 잔액을 분리하는 안을 구체화했다. 이전 확정본의 다음 행동/합산 입금/지급기일/시간범위 모순을 이 초안에서 제거했다.

남은 중요한 결정: 현업 자료가 SAP 미결 잔액과 입금 반영 근거를 제공하는지. 제공하면 이 계산 방식으로 어댑터를 만들고, 제공하지 않으면 추가 SAP 조회 경로를 먼저 설계한다. 은행 파일만 보고 SAP 미반영을 추정하지 않는다. 이번 문서 상세 설계에 대한 사용자의 재확인은 아직 받지 않았다.
