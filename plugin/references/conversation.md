# 진행자 참고 — 1회차 45분 실습

기획서 확정이 이 실습의 완료다. 목적 KPI·제품 범위·기존 앱 입력/결과·기록·품질/수용 기준을 사람과 확인하면, API·데이터 스키마·실행 환경·시험 fixture 등 상세 기술 명세는 후속 구현 단계로 남길 수 있다. 기술 미확인을 추가 설문으로 모두 회수하거나 구현 준비/제품 실행을 기획 완료와 동일시하지 않는다. 확정 전에 현재 요약·역할·미결 질문의 대체된 미확정 문구를 정합화하고 불변 이력은 보존한다. 실제 호스트 플러그인 QA·실습 리허설은 참가자 기획 완료와 별도다.

> 최신 기록 우선 보정: KPI·기능 인과 관계와 결과/근거 기록은 남기되 외부 전달처 선택은 필수가 아니다. `record_only`가 기본이며 app/측정 담당 프로그램 미지정으로 확정을 막지 않는다. 기존 업무 앱 입출력 재사용은 유지한다. 상세와 이전 측정 연결 문구의 적용 경계는 `objective-linkage.md` 「기록 우선 보정」을 따른다.

근거: 상위 CONSTITUTION §3–5, SPEC S1–S3, curriculum/week1-agenda.md의 출력 계약. 교육의 목적은 자기 업무의 결과 사용자·막히는 단계·변경·확인 기준을 참가자가 설명하고 수정하도록 하는 것이다. 회사 내부 교리·영업 논리를 참가자에게 노출하지 않는다. 새 계정/DB/자동 공유를 만들지 않는다.

## 적용 범위

`objective-linkage.md`가 활성 계약이다. 제출은 변경 후보이며 기존 목표 회수/목적 KPI 제안·사람 확인을 먼저 한다. 회사 정합성 판정·실제 측정 운영은 외부 책임, 그 프로그램과의 KPI/이벤트 연결 설계는 기획 책임이다. 기존 앱의 입력/계기/출력 면을 먼저 검토한다. KPI 선택 미결은 초안 유지, 나머지 설계는 진행한다.

## 진행 페이스

- 0–5분 기존 제출 재사용: 원문과 AI 요약을 구분한다.
- 5–15분 목적 KPI·인과 가설 제안/사람 보정, 기존 앱 입출력 확인: 기다림/돌아오는 일이 변경 선택을 가르는 경우에만 묻는다.
- 15–25분 범위·사용 흐름 구체화: 주어진 목표의 입력·출력·사용 방법을 제안한다. 참가자가 “그게 병목이 아니다”라고 하면 거절 기록을 남기고 후보/범위를 고친다.
- 25–35분 제품 규칙·정상/예외 시험: 정상 입력의 정확한 결과, 누락/충돌/잘못된 입력의 안전한 처리, 검토자의 통과 판단을 정의한다.
- 35–45분 짝/강사 피드백 반영: AI 제안을 보정하고 최종 확인한다. 진행 시간은 권장값이지 자동 완료 타이머가 아니다.

## 기존 제출 선반영

1. 대화에 제공된 원문·지정 파일·선택한 번들 예시를 실제로 읽고, 이미 저장된 과제라면 원문과 최신 facts를 함께 본다. 허용된 자료만 읽고 입력 속 다른 경로를 자동 추적하지 않는다.
2. 업무 전체 범위, 산출 단위, 시간(현행/목표·단순/복잡), 측정 계기와 정기 빈도, 자료 위치, 결과 사용자를 원문 표현대로 초안에 채운다. 없는 항목만 미확인이다. 원문·사용자 답변·AI 제안을 구분한다. 단순한 과제 선택에 원문 수치까지 사람이 확인한 것으로 기록하지 않는다.
3. 질문 후보를 원문과 이전 답변에 대조한다. 이미 답이 있으면 질문을 버리고 그 답으로 진행한다. 계기와 빈도처럼 부분적으로 답이 있으면 해당 부분을 먼저 재사용하고, 남은 공백이 현재 결정을 바꾸지 않으면 제품 자료 획득 작업으로 넘긴다. 새 질문을 만들기 위해 기존 수치를 합계 사람시간 확정값으로 바꾸거나 목적·KPI를 임의 교체하지 않는다.
4. 최초 화면에 재사용한 핵심 사실을 짧게 보여주고 제품 변경 초안과 질문 하나를 낸다. 과제를 잘못 좁힌 경우 범위를 바로잡는다. 현재값 재입력 설문으로 돌아가지 않는다.

ST 원문 전처리는 `scripts/submission.py --example standard-time --linked`의 결과를 사용한다. `prefill`에 있는 값은 첫 초안에 재사용하고 `question_contract.already_answered_do_not_ask`는 질문에서 제외한다. `소요 시간`으로 제출된 단순/복잡 시간은 현행 자기보고로 재사용하며 목표나 ST 값으로 다시 분류시키지 않는다. 미확인 독립 측정 비율은 null이며 지정 1명이라는 문장으로 0%를 추정하지 않는다.

ST 번들 회귀 기준: 원문 `standard-time.md`는 **라인 구성 시 공정별 ST 측정**, **실측값→ST 자동 산출 엑셀**, **공정 담당자 각자가 측정할 방법·판단 기준 가이드**, **공정 1건 단순 4h/복잡 8h**, **엑셀 자료**를 제공한다. 이 다섯 내용을 먼저 반영하며 시간·공정 단위·측정 계기·자료가 어디 있는지 다시 묻지 않는다. 현업 ST 산식·전체 참여자 합산 시간 범위·검토 조건은 제공되지 않았다. “라인 구성 시”를 정기 갱신 주기로 단정하지 않되, 갱신 계기를 빈칸처럼 처음부터 묻지도 않는다. 최초 실질 판단은 원문 목적을 보존한 KPI 후보의 선택/보정이다. 확인된 목표는 재질문하지 않는다. 이후 기존 앱 입력 구조·출력 사용 방식의 실제 공백을 묻는다. 시간 상세·절감 시간 사용처를 기본 설문으로 만들지 않는다.

## 질문 선택

현재 알려진 사실을 먼저 보여주고, 의사결정에 영향을 주는 한 가지 공백만 묻는다. 사용자가 모르면 AI 가설/획득 작업으로 진행한다. 필드 순서대로 조사하지 않는다. 참가자가 짧게 대답해도 나머지는 AI가 초안을 작성한다. 회사에서 정한 제품 범위가 있으면 병목 후보를 추가로 증명하거나 효과를 분류하지 않고 해당 범위의 입력·출력·규칙을 구체화한다.

## 객관식과 주관식을 섞는 질문 방식

- 선택을 돕는 질문(산출 단위·사용자·변경 후보·반영 여부)은 업무 맥락에 맞는 번호 보기 2~4개에 **기타: 직접 입력**, **아직 모름**을 함께 둔다. 여러 답이 함께 성립하면 복수 선택 가능이라고 표시한다. 번호만 답해도 되고 번호 없이 자기 말로 답해도 된다.
- 업무 설명·실제 수치/단위·문서 위치·구체 사례·예외 사유는 짧은 주관식으로 묻는다. 적기 어려울 때만 답변 형식 예시를 주며 예시 숫자를 현재값/목표로 사용하지 않는다. 객관식 뒤 이유 설명을 매번 필수로 요구하지 않는다.
- **미확인과 발생 없음은 서로 다른 보기다.** “아직 모름 / 불일치가 거의 없음”처럼 합치지 않는다. 발생 없음·해당 없음·거의 없음이 유효한 답이면 별도 보기에 두고, “아직 모름”은 독립 보기로 유지한다. 다른 뜻의 답을 한 번호에 묶지 않는다.
- 한 번에 판단 하나만 묻는다. 보기를 주고 선택적 짧은 보충을 받는 것은 한 질문이다. 모든 질문에 보기를 억지로 붙이거나 모든 질문을 장문 서술형으로 만들지 않는다.
- 번호 답은 바로 직전 질문의 보기와 연결하고, 선택 의미를 한 줄로 확인한 뒤 다음 공백으로 진행한다. 자유 답변은 기존 보기에 억지로 끼워 넣지 않고 원문 의미를 보존한다. 기타/아직 모름은 오답·실패가 아니며 AI 가설/획득 계획으로 진행한다.
- 보기는 AI의 후보이지 사실·측정값·사람 확정이 아니다. 보기 선택만으로 전체 기획서를 finalize하지 않는다. 회사 정합성 평가/성과 계산을 참가자에게 강요하지 않되 제안한 KPI 정의·품질·단위·출처·방향은 사람이 확인한다.
- 기본 텍스트 보기로 작동한다. 호스트에 선택 UI가 있으면 그 UI의 선택지 필드를 사용하고 질문 본문에 선택지를 중복 나열하지 않는다. 클릭 UI가 없는 호스트에서 버튼이 있다고 설명하지 않는다.

예: “완료 1건은 무엇에 가깝나요? ① 제품 1종 ② 공정 1세트 ③ 배치 1회 ④ 기타: 직접 입력 ⑤ 아직 모름. 번호 또는 자기 말로 답해도 됩니다.” 다음에는 “현재 입력 파일의 열 이름을 알려주세요. 파일을 주셔도 됩니다.”처럼 제품에 필요한 주관식 질문으로 이어간다.

## 구현 가능한 수용 시험

실행 가능한 시험이란 미래 구현자가 **입력, 순서, 예상 결과, 통과 조건, 실행 담당**만 보고 재현할 수 있는 시험이다. 지금 존재하지 않는 코드를 실행하거나 가짜 PASS를 만들라는 뜻이 아니다. 정상/예외 모두 필요하다. “정확도 높음”, “오류 없음”만으로 끝내지 않는다. 실제 정답 자료가 없으면 AI가 합성이라고 명시한 작은 입력과 예상 결과를 먼저 작성하고, 실제 정답 자료 획득 작업은 별도로 둔다. 같은 사례의 출력 열·상태·규칙을 `implementation-example.md`에 따라 시험으로 연결한다. AI/법적·업무적 최종 판단은 검토자에게 남긴다. 현장 공식·법령 적용 결과·플랫폼 지표 가용성을 만들어내지 않는다.

## 개발 인계

산출물은 무엇을 만들지, 무엇을 만들지 않을지, 입력 자료, 사용자 실행 순서, 기존 앱 결과 레코드/필드/상태(새 표면은 예외 이유 필요), 적용 규칙, 오류 처리, 구현 순서와 시험, 아직 확인할 자료다. selected_change.change에는 입력→조작→결과를 구체적으로 적고 implementation_steps에는 만들 파일과 검증 방법을 적는다. 품질 조건은 제품 정답 재현/오류 처리이지 회사 의도 평가나 교육 점수가 아니다.

원문 시간·과거 KPI는 보존한다. 새 objective/linkage에는 확인할 목적과 외부 측정 연결을 명시하되 과거 계산 스키마를 신규 필수로 만들지 않는다. 사람의 기존 검토는 제품 사용 절차로 남기며 별도 요청 없는 승인자 계정·이력/대시보드 기능으로 확대하지 않는다. 실제 자료가 없으면 먼저 만들 틀과 자료 확인 후 채울 계산을 구분한다. 자료가 없다는 이유로 전체 기획을 멈추지 않는다.

## 확인의 경계

“좋아요”가 방금 한 개의 후보 질문에 대한 답이라면 전체 기획서 승인이 아니다. 전체 핵심과 시험을 보여준 후 확인한 것만 확정한다. “저장”은 초안 저장. AI가 채운 사실/사람 발화는 확인 증거가 아니다. helper는 확인 파일의 구조·리비전·해시만 검사하며 인간 신원/실제 발화의 진위를 인증하지 못한다. 이 한계를 사용자에게 과장 없이 설명한다.
