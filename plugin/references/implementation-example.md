# 대표 사례에서 개발 착수용 명세 만들기

기획서 확정이 이 실습의 완료다. 목적 KPI·제품 범위·기존 앱 입력/결과·기록·품질/수용 기준을 사람과 확인하면, API·데이터 스키마·실행 환경·시험 fixture 등 상세 기술 명세는 후속 구현 단계로 남길 수 있다. 기술 미확인을 추가 설문으로 모두 회수하거나 구현 준비/제품 실행을 기획 완료와 동일시하지 않는다. 확정 전에 현재 요약·역할·미결 질문의 대체된 미확정 문구를 정합화하고 불변 이력은 보존한다. 실제 호스트 플러그인 QA·실습 리허설은 참가자 기획 완료와 별도다.

> 최신 기록 우선 보정: KPI·기능 인과 관계와 결과/근거 기록은 남기되 외부 전달처 선택은 필수가 아니다. `record_only`가 기본이며 app/측정 담당 프로그램 미지정으로 확정을 막지 않는다. 기존 업무 앱 입출력 재사용은 유지한다. 상세와 이전 측정 연결 문구의 적용 경계는 `objective-linkage.md` 「기록 우선 보정」을 따른다.

이 참고는 질문 수를 늘리는 설문지가 아니다. 참가자 대신 AI가 설계 초안을 만들고, 참가자는 실제 업무와 다른 부분을 보정한다. 기존 저장 스키마·불변 리비전은 유지한다. 업무 구현/외부 연결/시험 실행은 이 교육 플러그인의 실행 범위가 아니다. 기획서의 시험 코드나 입력 예제는 데이터로 저장하며 자동 실행하지 않는다.

## 생성 경로

1. 원문에서 확인한 입력·규칙과 미확인을 분리한다. 명세의 구현 제안(입력 열/키/화면/사용 흐름)과 실제 업무 판정(수정·회수액·합격·우선순위)은 다르다. 후자는 근거 없는 가정으로 채우지 않는다. 계산 결과뿐 아니라 표 아래 행동·질문 선택지도 같은 기준으로 검사한다.
2. **AR 단일 금액 사례:** 설치된 `scripts/example.py ar`를 한 번 실행한다. 금액/통화가 주어지고 인보이스-입금 대응을 전제로 하는 합성 사례에만 사용한다. 사용자 내용을 실행하는 도구가 아니다. 입력 근거가 없는 반영/시점은 `unknown`; 입금일은 생성하지 않는다. 도우미의 Markdown 전체(표와 질문 포함)를 그 턴의 최종 응답으로 그대로 사용한다. 계산/다음 행동뿐 아니라 질문 이유·선택지·전후 설명도 추가 생성하지 않는다. 저장 경로 한 줄 외 추가 문장은 금지한다. 예시 명령(수치는 자기 입력으로 교체):

   `python3 <plugin-root>/scripts/example.py ar --sap-open 600 --receipt 300 --currency EUR --posted unknown --aligned unknown --due 2026-09-01 --as-of 2026-09-07`

   `--posted yes`=이미 SAP 미결에 반영, `no`=미반영. `--aligned yes`=기준시점 정합 확인. "기준일이 있다"는 "시점 정합 확인"과 다르다. 지급기일/기준일 미제공이면 해당 옵션을 생략한다. 여러 입금/통화/취소·배분 규칙은 지원하지 않으므로 도우미 범위를 확대해 해석하지 않는다. 단일 통화·정확한 대응·다른 조정 없음은 합성 설계의 제한이며 실거래에 임의 적용하지 않는다.
3. **그 밖의 업무:** 원문 행을 하나 택하고 확인된 입력을 보존한다. 입력→제안 처리 순서→제안 출력의 구체 열/값→담당자 다음 행동을 제시한다. 규칙이 없는 셀만 `판정 미확정 — 필요한 기준`으로 둔다. 예: 제품명/모델/문서종류는 그대로 출력하고 법규 적합성은 근거 미확인, 실제 제출/허가 결론을 만들지 않는다. 회사 ST 산식이 미확인이고 수량·준비시간분·개당 가공시간분이 있다면 `example.py st --quantity 10 --setup 20 --per-unit 3`에 해당 입력을 넣어 AR과 동일한 최종 응답 계약을 적용한다. ST값뿐 아니라 ST 공식도 만들어내지 않는다. 기술적 구현 방식과 정상/결측 시험은 그 상태에서도 제안한다.
4. 대표 결과를 바꾸는 미확인 전제 하나를 질문한다. 원천 근거를 회수하는 질문을 우선하며, 문서를 진행시키지 못하는 반복 질문·정상/경고 같은 근거 없는 선택지·알려진 목적 재확인을 하지 않는다. 사용자 답이 오면 해당 입력을 바꿔 같은 경로로 다시 생성한다.

## 제품 범위와 사용자 실행면

`objective-linkage.md`의 목표 KPI·인과 가설을 먼저 확인하고 주어진 제약 안에서 제품을 구체화한다. 새로운 승인 시스템·측정 계산기를 붙이지 않는다. 기존 업무 앱의 원천 레코드→트리거→결과 레코드/필드/상태를 먼저 제안한다. 새 폼·파일 다운로드 제품은 기존 표면 재사용이 어려운 이유가 있을 때만 예외로 제안한다. 실제 필드가 아직 없으면 제안 열과 원천 열을 구분한다. 환경 미확인으로 제품을 중단하거나 특정 기술을 확정하지 말고 환경/원천 검사부터 구현 순서에 넣는다. 기존 기능으로 가능하면 재사용한다.

제품 요구의 구현 일치·산식 정답·오류 처리는 기술적 시험이다. 정합성 판정/실제 효과 측정은 외부 프로그램 소관이지만 목표 KPI와 측정 이벤트 연결 설계는 반드시 인계한다. 같은 사례 ID로 정상 이벤트 매핑·중복 억제·실패 시 성공 상태/측정 이벤트 미생성을 시험에 넣는다. 실제 외부 API 호출이나 성과 수집은 실행하지 않는다.

## 대표 한 건을 먼저 보여주기

기존 제출로 가능한 범위에서 `입력 → 처리 → 결과 → 사람 행동` 한 건을 작성한다. 실제 입력이 없으면 **합성 예시이며 실제 업무 규칙·정답은 미확정**이라고 먼저 표시한다. 초반에는 한 개의 작은 결과 표/행으로 충분하다. 실물 없이 합산/분할/시점 질문만 연달아 이어가지 않는다. 이미 답한 항목은 다시 묻지 않는다. 법령 판정·ST 공식 등 실제 전문 규칙은 합성 예시를 핑계로 만들어내지 않는다. 확인되지 않은 규칙은 기호 또는 명시적 설계 가정으로 유지한다.

예: AR 합성 입력에서 SAP 미결600, 이미 반영된 은행입금400, 미반영300이면 SAP600은 보존하고 미반영300과 회수 검토300을 다른 열로 보여준다. 이 가정은 실제 SAP 조회로 확인해야 한다. 합성 표시 하나가 모든 누락 전제를 대신하지 않는다. 입력에 반영상태가 없다면 먼저 “이 예시는 미반영을 가정”을 명시하거나, 결과를 “SAP 반영 상태 확인”으로 제한한다. 근거가 없으면 미반영으로 단정하지 않는다. 참가자에게는 “이 결과로 다음 작업을 할 수 있는가”처럼 가장 큰 차이 하나를 묻는다. 이 예의 EUR·날짜·숫자·SAP 선택을 다른 업무에 강제하지 않는다.

## 같은 사례를 기존 필드로 연결하기

- `workflow`: 현재 흐름은 제출 사실/확인 내용을 반영. 원천에서 어떤 작업이 남는지도 명시.
- `selected_change.change`: 제안 사용 흐름·출력 열/한 행·사람의 후속 행동. `non_goals`에 첫 버전 밖의 자동화 명시.
- `inputs[].source`: 원천 열과 내부 표준 필드를 구별하고 키·형식·기준시점을 설명. 미확인 원천 필드의 존재를 단정하지 않는다.
- `quality_conditions`: 유일키·잔액/기준값 출처·중복/정정/결측·상태 변화·수동 보정/취소 규칙. 남은 중요한 설계 선택과 임시 가정 구분.
- `acceptance_tests`: 대표 사례와 **같은 ID/값/날짜**를 사용해 정상·예외의 구체 입력, 예상 행/상태/금액, 통과 조건을 저장. “정답표와 일치”만 쓰지 않는다. 확보할 실제 정답과 합성 설계 정답을 구별한다. 정확한 계산이 필요하면 명세 작성자가 허용된 계산 도구로 확인하되 계획 안의 임의 코드를 실행하지 않는다.
- `responsibilities.ai`: 실행 중 AI가 불필요하면 “실행 시 사용하지 않음; 개발/명세 작성 지원”으로 적는다. AI 코딩 도구 사용과 제품의 LLM 호출을 혼동하지 않는다.
- `implementation_steps`: 첫 실행 환경·원본/결과 보관·실패/복귀·수동 판단 재개를 도구 규모에 맞게 명시. 장황한 운영 체크리스트를 강제하지 않는다.
- `comparison`: 레거시 호환 필드. 제품 모드에서 작성·질문·출력하지 않는다. 제품의 기술적 정상/예외 시험은 `acceptance_tests`에 유지한다.
- `next_action`: 문서 검토 중이라도 **확정 이후 실행할 다음 행동**과 완료 조건을 저장한다. “기획서 확정”을 최종 문서의 다음 행동으로 남기지 않는다.

미확인 항목은 원천·담당 역할·획득 방법·완료 조건을 둔다. 질문은 설계 범위를 바꾸는 한 가지에만 사용하고 나머지는 초안으로 보충한다. 모든 기술 선택을 사람에게 되묻지 않는다.

## 확정 전 의미 검사 — 진행자가 수행

1. 목표 KPI 정의·품질·단위·출처·방향·인과 가설은 사람이 확인했는가? 기존 앱/측정 연결은 bound 또는 명시적 획득 작업인가? 최신 사용자 답이 흐름·범위·규칙·시험·다음 행동에 모두 반영됐는가? 확인된 사실을 여전히 미확인으로 적거나 제외한 기능을 역할에 남기지 않는다.
2. 대표 사례의 식별자·금액·날짜·계산 기준이 출력과 시험에서 같은가? 기대 결과가 유효한 가정에서 도출되는가?
3. 한 문서 안에서 장부/검토 잔액, 합성/실제, 제안/확인, 계획/실행을 혼합하지 않았는가?
4. 원문에 시간 수치가 있더라도 제품 기획에서 baseline을 생성하지 않는다. 원문은 submission/facts에 보존하고 계산 입력·규칙·산출물만 구현 기획서에 반영한다.
5. 결과를 본 사람이 무엇을 하는지, 실패·애매함·재실행에서 어떤 상태가 남는지 설명됐는가?
6. 업무 방향 동의·상세 명세 준비·시험 실행·운영 검증을 별개로 보고하는가? helper의 `finalized`는 사람의 문서 확인이지 production-ready나 테스트 PASS가 아니다.

검사를 통과하지 못하면 진행자가 초안을 고친다. 구조검사 `validate --complete`로 의미 검사를 대체하지 않는다. 자동 검사가 이해/현업 타당성을 증명한다고 주장하지 않는다. 추가 가정을 넣어 고친 문서에 이전 확인 발화를 재사용하지 않는다.

## 작성 예시의 검증 범위

레포 `examples/germany-ar/implementation-spec.md`와 `reconcile.py`, `test_reconcile.py`는 운영자가 별도로 만든 합성 설계 실험이다. 참가자 플러그인은 이 코드의 자동 실행/도구 배포로 범위를 넓히지 않는다. 소스 repo가 없는 ZIP에서도 위 절차만으로 작업할 수 있어야 한다.
